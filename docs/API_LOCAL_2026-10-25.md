# Validação da API local — 25/10/2026

Atividade da [Issue #10](https://github.com/Fixa-Inter/segundo-aplicacao-website/issues/10), na branch `feature/integracao-api-web`. O usuário optou por executar a API localmente.

## Ambiente

API original do commit `1927e92cb36c335744b599e11d024593326d0265`, compilada com seu Dockerfile (Java 21/Maven), PostgreSQL 17, Redis 7, Serverless Redis HTTP, Nginx interno e Mailpit. O build do Dockerfile original pula os testes do backend; esta evidência é de execução integrada, não de aprovação da suíte Java.

Web em `http://localhost:5173`, API em `http://localhost:8080` e caixa de e-mail em `http://localhost:8025`. Os serviços publicados escutam somente no loopback; banco e Redis ficam internos. Credenciais geradas em `dev.local/stack.env` e `dev.local/acesso.txt`, ignorados pelo Git. Instruções reproduzíveis em [dev/README.md](../dev/README.md).

Bootstrap idempotente: instituição, unidade, gestor, turno Diurno e Auditório. Nenhum cadastro existente tem senha ou dados substituídos ao reiniciar. Os volumes de banco e Redis são preservados por `npm run local:down`.

## Verificação com serviços reais

Navegador Edge isolado, 1280×720, sem interceptação ou respostas HTTP simuladas. Perfil de acesso GESTOR. Dados exclusivamente sintéticos do ambiente local.

| Fluxo             | Resultado observado                                                                                                              |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| Saúde             | `GET /actuator/health` retorna `UP`                                                                                              |
| Login             | CNPJ, e-mail e senha autenticados; entrada nas rotas privadas                                                                    |
| Técnico           | Cadastro, ativação e vínculo ao turno; confirmação por GET independente                                                          |
| Competências      | Notas 0 e 10 gravadas; edição para 7 e remoção da outra avaliação, confirmada como inativa no servidor                           |
| Persistência      | Recarregamento da equipe e nova edição preservam os valores devolvidos pelo backend                                              |
| Calendário        | Evento criado com local e responsável reais; edição do título confirmada por GET                                                 |
| Perfil            | Nome atualizado e consultado no servidor; nome original restaurado ao final                                                      |
| Sessão            | Refresh rotacionado; reutilização do anterior recebe 401                                                                         |
| Recuperação       | Código de seis dígitos recebido no SMTP Mailpit, usado na web para definir nova senha; novo login realizado com a senha alterada |
| Troca autenticada | Senha inicial do gestor restaurada pela API após o teste e novo login confirmado                                                 |
| JavaScript        | Nenhum erro de página nos cenários percorridos                                                                                   |

Técnico e evento de QA permanecem no banco local para inspeção. A senha inicial documentada em `dev.local/acesso.txt` continua válida.

## Ajustes encontrados na execução

- O SMTP local precisava desabilitar explicitamente STARTTLS obrigatório e SSL; o Mailpit recebe as mensagens localmente sem autenticação externa.
- A ponte Redis respondia em HTTP/1.1, mas encerrava a tentativa HTTP/2 do cliente Java. A comparação das duas versões confirmou o problema. O Nginx interno adapta essa comunicação sem modificar o código original da API.
- O backend cria técnicos inativos. A web ativa o novo cadastro antes de vincular turno e aplica a situação final solicitada. Há teste de contrato cobrindo a criação com situação final Inativo.

## Escopo da confirmação

A execução confirma os fluxos acima na máquina local e no papel GESTOR. Os testes de contrato também cobrem permissões e falhas com respostas controladas. Não houve teste com o aplicativo mobile, implantação em produção, aprovação de outro integrante, merge ou homologação da equipe. Dashboard/BI, desempenho e Manu continuam dependendo de endpoints ausentes na API consultada.
